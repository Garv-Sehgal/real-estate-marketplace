CHAPTER 3: ASSIGNED JOB / INDUSTRIAL TRAINING


3.1 Introduction to the Assigned Job

During the 20-week industrial training tenure from January 2026 to May 2026 at **SPRWork Infosolutions**, I was assigned the role of **Junior Software Developer Trainee**. The primary objective of this assignment was to design, implement, integrate, and verify a commercial-grade, multi-role web platform: the **Real Estate Marketplace Platform**.

In my capacity as a Junior Software Developer, I was responsible for executing tasks across the entire application stack:

  • Requirement Synthesis: Participating in initial planning sprints to define structural requirements, user stories, and system limitations.
  • Database Modeling: Defining MongoDB schemas using Mongoose, establishing relations between user roles, property metadata, chats, and meetings, and creating search indexes.
  • REST API Design: Building modular, asynchronous Express server controllers, routing hierarchies, and role validation middlewares.
  • Frontend Engineering: Crafting responsive glassmorphic UI panels in Next.js 16 and React 19, managing complex form states, and implementing custom hooks.
  • Real-Time Signaling: Managing persistent Socket.IO rooms for instant messaging, dynamic badge counters, and real-time status updates.
  • Client-Side Cryptography: Implementing client-side AES symmetric key derivation and encryption using CryptoJS to support secure private chat negotiations.

3.2 Training Methodology

The industrial training at SPRWork Infosolutions followed a structured methodology designed to help trainees transition from academic programming to professional software engineering:

  1. Onboarding & Technical Orientation (Weeks 1–3): Training in the company’s standard coding guidelines, modular full-stack JavaScript architectures, asynchronous Express routing, and NoSQL modeling.
  2. System Specification & Architecture (Weeks 4–6): Conducting system requirements analysis for the Real Estate Platform, defining database schemas, and establishing API contracts between frontend and backend teams.
  3. Backend Construction Sprints (Weeks 7–11): Implementing Express routes, Mongoose models, authentication flows (JWT, OTP, password hashing), and Socket.IO namespaces.
  4. Frontend Construction Sprints (Weeks 12–16): Building modular Next.js components, managing form states, integrating client-side cryptography, and implementing responsive layouts.
  5. Integration, Testing, & Verification (Weeks 17–20): Integrating the frontend with backend APIs, conducting functional and integration testing, optimizing query speeds, and preparing the final documentation.

3.3 Core Technical Areas Practiced

The development of the Real Estate Marketplace required applying several core software engineering principles in practice:

  • Decoupled SPA-API Communication: Structuring the client and server as separate, decoupled entities that communicate using stateless REST APIs and JWT bearer tokens.
  • Flexible Data Modeling: Using a document-based NoSQL database (MongoDB) to handle flexible property pricing schemas and hierarchical location details without empty relational columns.
  • Persistent WebSockets: Establishing real-time, bi-directional signaling channels using Socket.IO to manage chat rooms and dynamic status syncs.
  • Client-Side Cryptography: Implementing browser-side AES encryption and key derivation, ensuring that private chat contents are encrypted in the client before being sent to the server.

  • Next.js 16 & React 19: Used for building the frontend Single Page Application (SPA), managing client-side layouts, and coordinate interactive states.
  • TailwindCSS v4: Used for UI styling, responsive layout grids, glassmorphic panels, and transitions.

  • CryptoJS 4.2 & BcryptJS 3.0: Used for client-side AES encryption and server-side password hashing.

3.8 Challenges Faced

Executing a full-stack, real-time application in an industrial environment presented several technical challenges. Below are the key obstacles encountered and the engineering solutions implemented:

3.8.1 Requirement Understanding (End-to-End Chat Flow)

The requirement for client-side encrypted messaging presented an initial conceptual challenge. In traditional chat systems, the server reads the message text, saves it in a database, and forwards it to the recipient. Under the zero-knowledge model, the server must act purely as an offline relay, storing only ciphertext. The challenge lay in deriving matching encryption keys on both clients without transmitting keys over the network.

Solution Implemented: The system uses a client-side key derivation function based on a shared conversation ID and a static salt. When a chat is loaded, both clients generate an identical key using: `SHA256(ConversationID + SALT)`. This derived key is used for CryptoJS AES encryption and decryption within the browser, keeping the central database blind to the conversations.

3.8.2 Environment Setup (CORS and Security Headers)

During integration, the decoupled frontend and backend (running on different ports locally) caused Cross-Origin Resource Sharing (CORS) blockages. The browser rejected local API requests, multi-file uploads, and socket handshakes.

Diagram displays Port 3000 (Next.js) sending requests across Port 5000 (Express Engine) through the CORS Allowed Origin whitelist middleware, enabling secure multi-origin operations.

Solution Implemented: We configured the Express backend's CORS middleware to whitelist the frontend origin, set `credentials: true` to support cookie transmissions, and configured the socket server origins to allow multi-origin communication.

3.8.3 Full Stack Integration (Client-Server Socket State Sync)

Integrating Socket.IO real-time events with React’s client-side state caused synchronization issues. When users switched active chat rooms, socket instances sometimes remained connected to previous rooms, leading to double-rendering and message leaks.

Solution Implemented: The frontend uses clean React lifecycle hooks to disconnect and cleanup socket listeners when components unmount or rooms change. The server uses explicit room exit and join triggers to keep active socket instances synchronized with active chat windows.

3.8.4 Debugging Complex Issues (Socket Drops on Mobile)

During mobile testing, switching between networks or putting the browser in the background caused active WebSocket connections to drop. This resulted in missed messages and unread notification counts getting out of sync.

Solution Implemented: The client-side socket configuration was updated with dynamic reconnection parameters (`reconnectionDelay: 1000`, `reconnectionAttempts: 10`). Additionally, a status-checking backend endpoint was built, allowing the client to fetch missed messages from the database upon reconnection.

3.8.5 Documentation Preparation (Academic Formatting Compliance)

Organizing two independent reports (Part A and Part B) within a single HTML file while maintaining continuous page numbering, strict CSS formatting boundaries, and separate front matter presented a final formatting challenge.

Solution Implemented: We developed a Python compiler script (`build_report.py`) that reads modular chapter files, applies a unified academic CSS stylesheet, enforces page breaks, and maintains consistent, continuous page numbering from Page 1 to Page 100+.
