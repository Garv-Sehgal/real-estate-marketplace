CHAPTER 3: PROJECT UNDERTAKEN


3.1 Project Overview

The **Real Estate Marketplace Platform** was designed, implemented, and verified as a fully decoupled full-stack Progressive Web Application (PWA). The system utilizes an **Express 5** headless API backend written in asynchronous Node.js, and a high-performance **Next.js 16** Single Page Application (SPA) frontend designed with **TailwindCSS v4** and **React 19** hooks. The database layer is managed through **MongoDB Atlas** using the **Mongoose** object data modeling (ODM) framework.

The project is engineered for role-based real estate operations: allowing Buyers and Tenants to search, geolocate, and compare properties; Landlords and Agents to list properties with government identification proofs; Staff and Admins to moderate uploaded listings; and participants to negotiate in real time using client-side encrypted chat rooms with an integrated visit scheduling coordinator. This chapter provides a detailed, component-level documentation of all core systems implemented within the codebase.

3.2 System Architecture

The platform utilizes a decoupled, modern multi-role architecture that separates the user interface layer from backend operations:

  • Client-Side PWA Layer (Next.js 16): Manages visual grids, component states, browser geolocations, local storages, and WebSockets. The client parses dynamic routes and renders pages progressively.
  • Headless API Layer (Express 5): Operates as a stateless backend engine. It processes client requests, runs validation schemas, manages active Socket.IO rooms, executes role-based middleware guards, and processes database operations.
  • Data Repository Layer (MongoDB Atlas): Operates as an active NoSQL document store, managing collections for users, listings, conversations, messages, and meetings, with optimized search indexes.
  • Notification Gateway Layer (Twilio & Nodemailer): Dispatches transactional verification codes via SMS gateways and SMTP mail relays.

3.3 Authentication System

A core objective of the platform is security and spam prevention during user registration and session management.

3.3.1 JWT Authentication

The system uses stateless JSON Web Token (JWT) authentication for session management. Upon a successful login API call (`/api/v1/auth/login`), the backend generates and signs two distinct tokens:

  1. Access Token: Signed with the user's ID, role, and username. It is configured with a short lifespan (15 minutes) and attached as a bearer token in the HTTP headers of all authorized Axios requests.
  2. Refresh Token: Signed with the user's ID and configured with a long lifespan (7 days). It is returned inside a secure, `httpOnly`, `sameSite: 'strict'` cookie. The client-side application cannot read this cookie, protecting it from Cross-Site Scripting (XSS) theft.

When a client’s access token expires, Axios interceptors automatically detect the HTTP 401 response and request a session refresh at `/api/v1/auth/refresh`. The server validates the refresh token cookie, checks that it is registered in the active session database collection, and returns a new access token without requiring the user to re-authenticate.

3.3.2 OTP Verification

To prevent automated registration spam, the system implements a dual-channel verification process. During registration (`/api/v1/auth/signup/request-otp`), the user's submitted profile data, password hashes, and roles are temporarily cached in an in-memory pending storage collection (`auth.pending.store.js`).

The server generates two distinct 6-digit numeric verification codes:

  • smsOtp: Dispatched to the user’s mobile number via the Twilio SDK.
  • emailOtp: Dispatched to the user’s email address via a Nodemailer SMTP transport agent.

To complete registration, the user must enter both codes at `/api/v1/auth/signup/verify-otp`. The server checks the submitted codes against the cached records. If both are valid, the user document is created in MongoDB, the temporary store is cleared, and session tokens are signed automatically.

3.3.3 Password Reset Mechanism

If a user forgets their password, they can trigger the password reset flow at `/api/v1/auth/forgot-password`. The server validates the account email, generates a temporary verification token, and dispatches a secure password reset link containing the token to the user’s email. When the user submits a new password via this link, the server validates the token, hashes the new password with Bcrypt, and updates the database, automatically revoking all active refresh tokens to secure the account.

3.4 Role Based Access Control

To manage authorization across the platform, the backend uses a role-based access control (RBAC) model. The system defines seven distinct roles, each mapped to a numeric authority level:

Table B3.1: Numeric Authority Levels and Permission Scopes

Role Definition Numeric Level Endpoint Mount Permissions Access Control Scope
Buyer / Tenant 1 `/meetings`, `/chat/conversation` Browse listings, initiate negotiations, and schedule site visits.
Landlord 2 `/property/`, `/meetings/incoming` List personal properties, upload deeds, and manage visit requests.
Agent 3 `/property/`, `/meetings/incoming` Manage client listings, broker negotiations, and schedule visits.
Staff / Admin 4 `/admin/properties/pending`, `/approve` Moderate listings, check deeds, and manage system parameters.
Super Admin 5 `/admin/create`, `/admin/suspend` Full system management, including user suspensions and staff provisioning.

The backend authorization checks are enforced by the `requireLevel(minLevel)` middleware. When an authorized route is called, this middleware extracts the user's parsed JWT level from the request object and validates it against the minimum required authority level before executing the controller logic.

The property listing system allows landlords and agents to upload detailed property information through an intuitive, multi-step process managed by the `ListingStepper.js` frontend component. The form wizard is organized into five steps:

3.6 Property Search and Filtering

To support property discovery, the platform features a multi-criteria search and filtering system. The search controller (`/api/v1/property/search`) parses query parameters and builds dynamic queries using Mongoose:

  • Locality Matching: Uses case-insensitive regex matching on city and locality fields to return relevant listings.
  • Dynamic Range Queries: Parses minimum and maximum limits, matching against both rental rates (`pricing.monthlyRent`) and sale prices (`pricing.expectedPrice`) using logical operators.
  • Amenity Filters: Uses Mongoose arrays to filter properties that match all checked amenities (e.g., Gym, Pool, Parking).

To ensure fast search speeds as the database grows, indexes are configured on location (`location.city`), pricing (`pricing.expectedPrice`, `pricing.monthlyRent`), and review status (`review.status`) fields.

3.7 Property Comparison Feature

The comparison module allows users to select up to four properties and evaluate their technical parameters side-by-side:

  1. Selection Mechanics: Users add listings to their comparison queue by clicking checkboxes on property cards. The application stores selected IDs in the URL query string (e.g., `/compare?ids=ID1,ID2`).
  2. Grid Rendering (`app/compare/page.js`): This page parses the property IDs, fetches listing details in parallel, and displays them in a side-by-side grid comparison matrix.
  3. Structured Comparison Parameters: The matrix compares key details including category, type, BHK configuration, carpet area, face direction, pricing models, and nine core amenities (Gym, Pool, Parking, Security, Club House, Garden, Power Backup, Concierge, Wifi), displaying visual checkmarks or cross marks for each parameter.

3.8 Property Approval Workflow

To prevent fraudulent listings, all newly created properties are initialized with an administrative status of `pending`. The listing remains hidden from public search results and marketplace views until approved:

  • Admin Auditing: Administrators use a moderation dashboard to review pending listings, audit government IDs, and check property deeds.
  • Status Transitions:
    • `approved`: The listing is made visible to the public.
    • `changes_requested`: The listing is flagged, and the landlord is prompted to update specific fields or re-upload documents.
    • `rejected`: The listing is flagged as fraudulent and permanently hidden.

3.9 Property Map View

The platform features an interactive map view powered by **Leaflet** and **React-Leaflet**.

During property creation, the frontend requests the browser's GPS coordinates to geotag the property location. In the property detail view (`app/properties/[id]/page.js`), these coordinates are used to display a map marker.

The details panel also features a direct redirection button to Google Maps navigation: 

const handleRouteRedirect = (lat, lng) => {
    if (!lat || !lng) return;
    const url = `https://www.google.com/maps/dir/?api=1&destination=${lat},${lng}`;
    window.open(url, '_blank');
};

This redirection provides buyers and agents with routing directions directly in their native map applications.

3.10 Property Image Upload System

Uploaded files are handled securely using the **Multer** storage engine:

  • Size Limits: The server enforces a maximum file size of 5MB per upload.
  • MIME Type Validation: The system restricts uploads to approved MIME types (like `image/jpeg`, `image/png`, and `application/pdf`) to prevent malicious script uploads.
  • Secure Disk Storage: Uploaded files (including cover images, property galleries, deeds, and government IDs) are stored in secure local upload directories.

3.11 Real-Time Chat System

Communication is powered by a real-time messaging pipeline built on **Socket.IO**:

  • Socket Handshake and Room Join: Upon logging in, the client connects to the WebSocket server and joins a private socket room named after their user ID. When entering a chat room, the client joins a conversation-specific room.
  • Event Signals: Sockets relay events for messages, typing status indicators, dynamic notification badges, and real-time scheduler updates.
  • Reconnection Management: The frontend implements reconnection logic to automatically restore WebSocket connections if network drops occur.

3.12 End-to-End Message Encryption

To ensure user privacy, the platform implements a zero-knowledge communication model using client-side symmetric AES encryption powered by **CryptoJS**:

  1. Key Derivation: When opening a chat room, the client generates a unique symmetric key using: `SHA256(ConversationID + SALT)`. This key remains in the browser's memory and is never sent to the server.
  2. Message Transmission: The sender encrypts the message text using CryptoJS AES before emitting it over the socket. The Express backend receives the ciphertext and saves it directly in MongoDB under the `encryptedMessage` field. The server acts as a blind relay and has no access to the decryption keys.
  3. Message Decryption: When the recipient's browser receives the encrypted event, it derives the matching key and decrypts the ciphertext, displaying the message in plain text.

3.13 Visit Scheduling System

The platform features an integrated site visit coordinator that allows buyers to request physical property visits directly from the chat timeline:

  • In-Chat Request Cards: Buyers fill out a scheduler dialog (date, time, message), which dispatches an interactive card to the chat timeline.
  • Dynamic Scheduler Cards: The timeline renders these cards with action buttons, allowing the landlord or agent to confirm, reject, or suggest a reschedule directly from the chat view.
  • Status Transitions: Updates to the visit status are pushed in real time over WebSockets, synchronizing the dashboard view of both parties instantly.

3.14 Notification System

The notification engine manages both real-time in-app pushes and external transactional notifications:

  • WebSocket Push Notifications: Real-time event dispatches immediately update unread badge counters in the navigation bars of active users.
  • SMTP Transactional Emails: Nodemailer SMTP helpers dispatch detailed notification emails when visit status changes occur (e.g., when a visit is confirmed, rescheduled, or cancelled), ensuring users are kept up-to-date even when offline.

3.16 Backend Architecture

The Express backend follows a clean, modular architecture. Key backend layout patterns include:

  • Controller-Service-Repository Pattern: Code is organized into modular layers to separate concerns: routes handle HTTP requests, services manage business logic, and repository models interact with the database.
  • Asynchronous Express 5 Routing: Leverages modern Express routing features to manage asynchronous operations cleanly without blocking the main event loop.
  • Global Error Handling Middleware: Intercepts unhandled errors, formats stack traces, and returns clean JSON responses to the client, preventing server crashes.

3.17 Frontend Architecture

The frontend is built on Next.js 16’s App Router. Key frontend structural configurations include:

  • Layout Providers: Wrap pages with context providers to manage authentication states, Axios HTTP interceptors, and socket client instances.
  • Custom React Hooks: Encapsulate interactive states, API integrations, and socket listeners (such as `useSocket` and `useListingForm`) for clean, reusable component logic.
  • TailwindCSS Glassmorphism: The UI uses transparent backgrounds, backdrop filters, and subtle borders to present a premium visual aesthetic.

3.20 Challenges Faced During Development

Full-stack system development presented several technical challenges:

3.20.1 Authentication and Security Challenges

Enforcing dual-channel OTP verification required managing temporary registration profiles securely. Storing pending details in the main database collection before verification would clutter the database, while in-memory variables could lead to data loss during server restarts.

Solution: A lightweight collection was structured to cache pending signups with a short Time-To-Live (TTL) index of 15 minutes, automatically removing unverified credentials from MongoDB.

3.20.2 Real-Time Communication Challenges

Battery optimization and network switches frequently drop active WebSocket connections on mobile devices, leading to missed messages.

Solution: The frontend client was configured with dynamic reconnection parameters. A database polling route was built as a fallback, allowing the client to fetch missed messages from the database upon reconnection.

3.20.3 Database Design Challenges

Real estate properties involve varying pricing structures. Rental listings require monthly rent and deposits; PG listings require rent per bed and utility inclusions; and purchase listings require property tax and expected pricing. Handling these models in a relational database would require complex schemas and empty columns.

Solution: Leveraging MongoDB's document architecture, a single, flexible nested property schema was built using conditional document validation.

3.20.4 Performance Optimization Challenges

Querying large listing collections with multiple filters (city, BHK, price range, amenities) caused slow API response times under simulated load.

Solution: Compound indexes were created on `location.city`, `review.status`, and pricing fields, reducing database scan times.

3.20.5 UI/UX and Integration Challenges

Managing complex forms in the stepper wizard risked losing user inputs if accidental page refreshes occurred.

Solution: Stepper form states were serialized in `sessionStorage` in the browser, allowing the frontend to restore form states if the page reloaded during upload.
